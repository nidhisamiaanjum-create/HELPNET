HELPNET development handbook

Everything from an empty computer to a merged pull request.

HELPNET is one platform that carries several community services for Bangladesh: blood donation, volunteer gathering, health experience sharing, second-hand goods, waste pickup and direct farmer sales, held together by one account system, one notification service and one admin toolkit.

Its guiding rule is connection only. HELPNET introduces and verifies people, then steps back. It does not take payments, hold money or arrange delivery.

How to use this page

Read the setup section once, on the day you join. After that you will mostly live in two places: the Task map, where your task card tells you exactly what to build and which commands to run, and the Git and GitHub section when something goes wrong.

utf8mb4 is not optional

HELPNET's default interface language is Bangla. A database created with the older utf8 character set will mangle Bangla text.

Why .env must never be committed

First, your database password and the app's signing key become visible to anyone with repository access. Second, whoever holds SECRET_KEY can forge a valid JWT and act as an administrator. Third, Git history is permanent: deleting the file in a later commit does not remove it from history. The only real fix is to change the password and generate a new SECRET_KEY.

The DRF Browsable API is your testing tool

http://127.0.0.1:8000/api/

Every endpoint appears as a clickable page with a form for its fields. Click, fill, press POST or GET, read the response. This is how backend tasks are tested before any screen exists.

The shape of a DRF view

  1. Validate — the serializer has already rejected the wrong shape; you check the business rules.
  2. Authorise — permission_classes handles the role check; add ownership checks in get_queryset or perform_update.
  3. Check conflicts — duplicate phone, closed opportunity, and so on.
  4. Do the ORM work — create, update or delete through the Django ORM.
  5. Return a serialised response — only the fields the serializer explicitly exposes.

Why the serializer matters

If you use fields = "__all__" or return the model directly, you return every column including the password hash. A serializer is a deliberate list of what may leave the server. It is the cheapest security control in this project.

Frontend setup

HTML, CSS and plain JavaScript talking to Django.

The frontend is three plain files per screen: HTML, CSS, JavaScript. No build step.

The full round trip

HTML → JavaScript → fetch() → Django → MySQL → Django response → JavaScript → HTML

A POST with fetch()

const API = "http://127.0.0.1:8000";

async function register() {
  const phone = document.getElementById("phone").value.trim();
  const password = document.getElementById("password").value;
  const btn = document.getElementById("submitBtn");
  const errorBox = document.getElementById("error");

  errorBox.textContent = "";
  btn.disabled = true;

  try {
    const response = await fetch(API + "/api/auth/register/", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ phone: phone, password: password })
    });

    const data = await response.json();

    if (!response.ok) {
      errorBox.textContent = data.detail || data.phone?.[0] || "Registration failed.";
      return;
    }

    window.location.href = "verify-otp.html";
  } catch (err) {
    errorBox.textContent = "Cannot reach the server. Is the backend running?";
  } finally {
    btn.disabled = false;
  }
}

A GET on a protected screen

async function loadMyProfile() {
  const token = localStorage.getItem("helpnet_token");

  const response = await fetch(API + "/api/auth/me/", {
    headers: { "Authorization": "Bearer " + token }
  });

  if (response.status === 401) {
    window.location.href = "login.html";
    return;
  }

  const user = await response.json();
  document.getElementById("name").textContent = user.name;
}

Four responses, every time

Every call has four possible endings: it worked, the input was rejected, the user is not allowed, or the server could not be reached. Screens that only handle the first one are the most common source of bug reports on student projects.

Git and GitHub

The workflow every task follows.

GITHUB → CLONE → BRANCH → CODE → TEST → COMMIT → PUSH → PULL REQUEST → REVIEW → MERGE → DELETE BRANCH → PULL MAIN

Start a task

git checkout main
git pull origin main
git checkout -b feature/T1.1.3-implement-registration-api

Always branch from a freshly pulled main.

While you work

git status
git diff
git add .
git commit -m "feat(auth): implement registration API"

Share it

git push -u origin feature/T1.1.3-implement-registration-api

Open the pull request

  1. Open the repo on GitHub. Press Compare & pull request.
  2. Direction must be your branch → main.
  3. Title it with the task id, e.g. T1.1.3 — Implement registration API (phone + password).
  4. Describe what you built, how you tested it, anything unfinished.
  5. Request a reviewer: Shakil for behaviour, Arnob for scope.
  6. Create the pull request. Do not merge it yourself.

After review

git checkout main
git pull origin main
git branch -d feature/T1.1.3-implement-registration-api

Fix review comments on the same branch and push again. Merge with Squash and merge.

Never commit directly to main

main is the branch everyone pulls from and the demo runs on. A broken commit on main blocks four other people at once.

What if Git says CONFLICT?

A conflict is normal. Two people changed the same lines and Git refuses to guess.

What it looks like

<<<<<<< HEAD
    phone = data.get("phone")
=======
    phone = data.get("phone_number")
>>>>>>> feature/T1.1.5-login-api

Resolve it

  1. Open each conflicted file in VS Code.
  2. Decide what the file should say. If unsure, ask the other person.
  3. Delete all three marker lines.
  4. Save, run the app, test the affected feature.
  5. Stage and commit.
git add .
git commit -m "fix: resolve merge conflict in auth views"
git push

Authentication

Registration to logout, in plain language.

REGISTER → OTP → LOGIN → JWT → PROTECTED REQUEST → ROLE CHECK → LOGOUT / RESET
  1. Register — the client POSTs phone + password to /api/auth/register/. The serializer validates the phone, hashes the password with bcrypt, and creates the user as unverified.
  2. OTP — a six-digit code is generated, stored with an expiry, and sent by SMS. The account stays unverified until the correct code comes back before it expires.
  3. Login — djangorestframework-simplejwt's TokenObtainPairView receives phone + password, checks against the hashed password, and returns access and refresh tokens.
  4. JWT issued — the access token contains the user id, expiry and any claims you add.
  5. Protected request — the browser sends Authorization: Bearer <access>.
  6. Role check — DRF's authentication class verifies the token; permission_classes checks the role; ownership is checked in the view or queryset.
  7. Logout — the browser deletes its token. Refresh tokens can be blacklisted server-side with token_blacklist.
  8. Password reset — a single-use, short-lived token is stored and emailed or SMSed, then exchanged for a new password via set_password.

JWT in plain language

A JWT is three parts separated by dots. The first two are readable by anyone; the third is a signature made with a key only the server knows. A user can read their token and edit the role to "admin", but they cannot produce a matching signature without SECRET_KEY. The backend checks the signature first and rejects the token.

Two mistakes that undo all of this

Trusting the role sent in the request body. The role comes from the verified token.

Checking permissions only on the frontend. Hiding a button hides nothing. If the check is not in the endpoint, it does not exist.

Custom user model — decide before the first migration

HELPNET needs a phone-based login, a role field, a verification flag and a language preference. That means a custom user model in apps.users and AUTH_USER_MODEL = "users.User" in settings.py. Set this before you run makemigrations for the first time. Changing it later requires wiping the database.

How to share a database across the team

Git does NOT sync database rows

When your teammate runs git pull, they get your updated .py files — they do not get the row you just inserted into users_user. Their MySQL is a separate service on their own machine with its own helpnet_db. There is no way to make git pull bring rows across.

ItemGit syncs it?
models.py change (new field)✅ Yes
Migration file✅ Yes
.env with your MySQL password❌ Never (correct)
Rows in your users_user table❌ No — they stay on your machine
Seed test dataOnly if you commit a seed.sql file and each teammate runs it manually

Your three real options

Option A — Each dev has their own local DB (recommended for daily work). Everyone runs MySQL locally, applies migrations, and has their own throwaway test data.

Option B — One shared remote MySQL (if you truly need shared rows). Rent a free MySQL on Railway, Render, Aiven or freesqldatabase. Everyone's .env points to the same DB_HOST, DB_USER, DB_PASSWORD. A registration made by one person appears in everyone's browser. Trade-offs: one bad migration wipes everyone's data, credentials must be distributed outside Git, and free tiers sleep or hit connection limits.

Option C — Deploy the backend + DB together (best for demo week). Deploy Django + MySQL to Railway or Render. Frontend points at the deployed URL.

What NOT to do

  • Do not commit a .sql dump of your working database. Real phone numbers, hashes, NIDs, messages — and once in Git history, permanent.
  • Do not use SQLite with the .db file committed to Git. It causes binary merge conflicts.
  • Do not expect git pull to bring rows. It never will.

Practical recommendation for this team

  1. Day-to-day: each dev has their own local helpnet_db, runs python manage.py migrate, and loads docs/seed_data.sql (fake accounts only — phone 01700000000, password testpass123, etc.).
  2. Integration/demo week: spin up a shared MySQL on Railway, update .env on every machine to point at it, run migrations once from one machine, load seed data once, demo from that.
  3. Write this decision into the README on day one.

Security

Applied while building.

Password hashing

Passwords hashed with bcrypt before touching the database. Configure PASSWORD_HASHERS to use bcrypt. Never store a password as text, never log it, never return it.

JWT tokens

Signed with SECRET_KEY. Browser sends Authorization: Bearer <access>. A user can read their token but cannot edit the role without breaking the signature.

Server-side role checks

Every protected endpoint checks the role itself via permission_classes. Hiding a button hides nothing.

Ownership checks

A citizen may edit their own listing. Every update and delete must confirm the record belongs to the caller, or that the caller is an admin.

Input validation

DRF serializers reject wrong shapes. Add business rules on top.

File upload validation

Check file type, cap size, generate a new random filename, store outside the web root.

NID and document protection

Only an admin may view. Everyone else sees a badge. Access is written to the audit log (FR9.5).

Privacy controls

FR1.5 privacy flags are applied in the backend before the response is built. A field hidden with CSS is still in the network response.

.env protection

Listed in .gitignore. If committed once, treat it as public: rotate SECRET_KEY and change the DB password.

Secret key protection

Development and production use different keys. A leaked key lets an attacker mint an admin token.

Admin protection

Admin accounts created deliberately via createsuperuser or a management command. No 'make me admin' endpoint.

SQL injection prevention

Use the Django ORM. Never build a raw query by joining strings with user input.

Never trust the frontend

Anything the browser sends can be edited. The backend re-checks everything.
