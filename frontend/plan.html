6 Sprints 5 Members HTML + CSS + JavaScript + Django 5.2 + MySQL Docker Render

HELPNET Project Scope

Core Community Services

Health

Community health suggestions and access to verified health professionals. Health content must clearly show that it is not a replacement for professional medical advice, and HELPNET must not claim to diagnose users.

Blood Donation

Find suitable blood donors and connect requesters with available donors based on blood group and location.

Volunteering

NGOs create events and volunteers can discover, join, attend and receive certificates.

Goods Exchange

Users can post second-hand goods and show interest in available listings.

Waste Management

Users submit waste pickup requests. Waste collectors/vangariwalas do not create HELPNET accounts; contact is by phone.

Farmer Marketplace

Farmers can publish products and users can browse available agricultural products.

Out of scope: in-app payments, native mobile applications and real-time chat.

Final Technology Stack

Frontend

  • HTML, CSS and Vanilla JavaScript
  • fetch() for API calls
  • frontend/pages/, frontend/js/, frontend/js/components/
  • frontend/js/api.js – configurable base URL (e.g., via window.API_BASE_URL or a setting)
  • frontend/js/auth.js for JWT/auth state, logout and role helpers
  • Nginx for serving the static frontend

Backend

  • Python 3.12 + Django 5.2 + Django REST Framework
  • Gunicorn (WSGI) for production
  • Django ORM + mysqlclient (MySQL driver)
  • djangorestframework-simplejwt for JWT authentication
  • Django CORS headers middleware
  • Custom User model (extends AbstractUser) – decided from the start

Database & Services

  • MySQL 8.x
  • Cloudinary for uploaded files; URLs stored in MySQL
  • Django's built-in email backend + SMTP for email announcements
  • ReportLab for volunteer certificate PDFs
Scope boundary: The frontend remains plain HTML/CSS/Vanilla JavaScript, the backend remains Python/Django/Django REST Framework, and communication remains email plus in-app notifications. Waste collectors/Vangariwalas never receive HELPNET accounts.

Frontend folders

  • js/pages – page-specific Vanilla JavaScript modules
  • js/components – reusable DOM/UI modules
  • pages – static HTML page views
  • js/api.js – shared API helpers using fetch(), base URL configurable via window.API_BASE_URL
  • js/auth.js – JWT storage, authentication state, logout and role helpers
  • js/utils.js – shared small frontend utilities
Routing: This is a static HTML application. Navigation uses separate files such as pages/login.html, pages/register.html and pages/profile.html; JavaScript auth guards redirect between these pages. There is no client-side single-page router; navigation uses separate static HTML files.

Backend folders

  • apps/ – Django apps, each containing models, views, serializers, urls, admin
  • helpnet/settings/ – environment-specific settings (base, local, production)
  • helpnet/urls.py – root URL configuration
  • apps/common/ – shared utilities, mixins, base models, custom permissions
  • tests/ – project-level test suite

5‑Member Git Workflow

Branch Strategy

  • main – production-ready code (protected)
  • develop – integration branch (all features merge here)
  • feature/* – one branch per task (e.g. feature/auth-register, feature/nid-verification)

Before starting work

git checkout develop
git pull origin develop
git checkout -b feature/your-task-name

During work

git status
git add .
git commit -m "feat(scope): description"

Push & PR

git push -u origin feature/your-task-name

Open a Pull Request from feature/your-task-name → develop. At least one reviewer (another team member) must approve. Never push feature work directly to main.

✔ Who reviews? The team lead or a member who is not working on the same feature. Rotate reviewers to share knowledge.

Preventing Conflicts

  • Ownership: Assign specific files/features to each member (see team table).
  • Shared files: backend/helpnet/urls.py, backend/helpnet/settings/ and backend/requirements.txt – coordinate via daily stand-up.
  • DB schema: One person (e.g. Samia) owns all migration files.
  • JavaScript components: Build isolated DOM/UI modules; share via frontend/js/components/.
  • Environment files: Never commit .env; use root and backend .env.example templates as sources of truth.
If two people must edit the same file:
1. Both pull latest develop before starting.
2. The first to merge resolves any conflicts with the second via a quick sync.

Sprint 1 – Authentication 3 tasks

Task: Register

Database

  • Custom User model (extends AbstractUser)
  • Fields: id, phone (used as username), password, role, full_name, created_at, updated_at
  • Constraint: phone UNIQUE

Backend

  • Model: apps/users/models.py
  • ViewSet/APIView: apps/users/views.py – register()
  • Route: POST /api/auth/register
  • Django's built-in password hashing (PBKDF2) + validation (phone, password strength)

Frontend

  • Page: frontend/js/pages/register.js
  • Form with phone, password, full_name, role
  • Client validation (phone format, password length)
  • API service: frontend/js/api.js

Testing

  • ✔ Valid registration → 201 Created
  • ✔ Duplicate phone → 409
  • ✔ Weak password → 400
  • ✔ Missing fields → 400
Git: feature/auth-register  |  Commit: feat(auth): add user registration API and page  |  PR → develop

Task: Login & JWT

Database

  • Same User model (check password via Django's check_password)

Backend

  • View: login() – verify password, issue JWT using djangorestframework-simplejwt
  • Route: POST /api/auth/login
  • Permission classes: IsAuthenticated, custom role-based permissions

Frontend

  • Page: frontend/js/pages/login.js
  • Store the JWT in localStorage through frontend/js/auth.js
  • Redirect to dashboard after login

Testing

  • ✔ Correct credentials → 200 + token
  • ✔ Wrong password → 401
  • ✔ Invalid phone/password → 401 (same response whether or not the phone exists)
Login rule: Valid credentials return 200. Invalid phone/password combinations return 401 Unauthorized without revealing whether the phone number exists.
Git: feature/auth-login  |  Commit: feat(auth): implement login and JWT flow

Task: Role & Protected Routes

Backend

  • Django REST Framework permission class: IsAuthenticated + custom HasRole permission
  • Apply to protected views using permission_classes

Frontend

  • JavaScript auth module: frontend/js/auth.js – store/read JWT, check auth state, logout, redirect unauthenticated users, and provide role-check helpers

Testing

  • ✔ Unauthenticated → redirected to login
  • ✔ Wrong role → 403
Logout: JWT logout is client-side: localStorage.removeItem("access_token"), clear local auth state, then redirect to the login page. No token blacklist is required.
Git: feature/auth-roles  |  Commit: feat(auth): add role-based guards and protected routes

Django Migration Strategy

Django models define the database structure, and Django's built-in migration system is the single schema-migration engine.

backend/
├── manage.py
└── apps/
    └── users/
        ├── models.py
        └── migrations/        # auto-generated by Django
  • Django migrations are auto-generated with python manage.py makemigrations.
  • Apply migrations with python manage.py migrate.
  • Do not maintain a second competing migration mechanism.
  • database/migrations/ remains a project folder for database-related artifacts only; it is not used as the schema migration engine.

Deployment (Render)

Backend

  • Runtime: Python + Django
  • Build: pip install -r requirements.txt
  • Start: gunicorn helpnet.wsgi:application --bind 0.0.0.0:$PORT
  • Env: MySQL credentials, DATABASE_URL, JWT_SECRET and service secrets
  • Migrations: Run python manage.py migrate as part of the deployment process (e.g., in a pre‑start script or a one‑off job). Do not rely on Render's paid pre‑deploy feature.

Frontend

  • Type: Static HTML + CSS + JavaScript
  • Build: None required
  • Publish: frontend/
  • API: Set the Django base URL in the frontend by defining window.API_BASE_URL in each HTML page or via a global script. For production, this points to the deployed backend URL.

Database

  • Use MySQL 8.x.
  • Run Django migrations with python manage.py migrate as an explicit deployment step (for example, a Render Start Command that includes the migration). The database/migrations/ folder is reserved for project artifacts only; Django's migrations/ folders inside each app are the sole migration source.
  • Django ORM + mysqlclient provide the Python database layer.
Render architecture: Frontend is a Render Static Site serving HTML/CSS/Vanilla JavaScript; backend is a Render Web Service running Django + Gunicorn; MySQL is a separate MySQL 8.x service reachable privately/internal where possible.
CORS: Configure Django CORS headers with django-cors-headers and an explicit allowlist. Development may allow the local frontend origin (for example, the local Nginx origin); production must allow only the deployed Render Static Site origin. Do not use CORS_ALLOW_ALL_ORIGINS=True for the authenticated production application. Store production secrets in the deployment platform, never in Git.
